==============================为什么实际分配内存失败======================================
vLLM 按共享缓存池计算容量，而当前 Ascend 路径为各层创建了独立缓存，导致实际显存成倍增加。

以 PP3 为例，可以沿日志完整对上：

| 步骤 | 日志结果 |
|---|---|
| PP3 上报预算 | 20.32 GiB |
| 规划中每个池块大小 | 262144 bytes，即 256 KiB |
| PP3 初始算出的块数 | 83240 |
| 所有 worker 统一后的块数 | 21175 |
| 规划认为最终池大小 | 5.17 GiB |
| Ascend 按 16 个缓存分别分配 | 82.71 GiB |



===============预算为5.17GB=============
21175 是 PP0 决定的。 PP0 的预算约 15.51 GiB，规划每块大小为 768 KiB：

PP0：预算 ÷ 每块大小 = 21175 个块
所有 worker 取最小块数 → 都使用 21175

这一步见块数统一日志 (start_2.log:515)。

问题出现在这之后。对 PP3，规划认为：

21175 × 256 KiB = 5.17 GiB，共享池总大小

它生成了 16 个描述，每个描述都标有相同大小。规划日志 (start_2.log:556)中的这些描述，不能简单理解为要申请 16 份独立内存。

“16 个缓存”指 PP3 上的 8 层，每层各有两类缓存，共 16 份。 

PP3 承载模型第 21～28 层，一共 8 层。每层都有：

| 缓存类型 | 用途 |
|---|---|
| attention KV cache | 保存之前 token 的 K、V，供后续注意力计算复用 |
| index cache | 保存索引信息，供稀疏注意力选择要关注的 token |

所以：

8 层 × 每层 2 类缓存 = 16 份缓存


================实际分配82.71GB==============
但 Ascend 当前逐层分配方式对应的是：

每个缓存 5.17 GiB × 16 个缓存 = 82.71 GiB

Ascend 接收配置的日志 (start_2.log:837)和后面的实际申请验证了这一点。

为什么容量检查会通过：PP3 检查认为支持 150000 token 需要约 3.35 GiB 的共享池，小于其 20.32 GiB 预算；但后端执行的是独立分配方式。

现在可以把排查范围收敛到 vLLM 共享池规划与 Ascend V2 分配、缓存访问方式的兼容性。修复时不能只把 16 份内存直接指向同一个地址，还必须确认后端按共享池的块编号和布局正确访问，否则可能互相覆盖数据。






=================为什么0.8时预算内存不足=============

PP8 在 0.8 时预算不足，直接瓶颈是 PP0：它的 profiling 激活峰值达到 33.20 GiB，其他 stage 只有约 3.22 GiB。

根据这次日志整理如下，单位为 GiB：

| Stage | 权重 | profiling 激活峰值 | 其他计入开销 | 0.9 KV 预算 | 推算 0.8 KV 预算 |
|---|---:|---:|---:|---:|---:|
| PP0 | 33.74 | 33.20 | 0.130 | 15.51 | 6.33 |
| PP1、PP2 | 51.86 | 3.22 | 约 0.044 | 27.45 | 18.27 |
| PP3～PP6 | 58.99 | 3.22 | 约 0.044 | 20.32 | 11.15 |
| PP7 | 54.15 | 3.22 | 0.057 | 25.14 | 15.97 |

最后一列是假设其他开销不变，从 0.9 日志换算得到的；PP0 的结果与之前 0.8 报错中的 6.33 GiB 一致。

PP0 的账是这样算的：

设备实际容量：91.75 GiB
0.8 允许使用：91.75 × 0.8 = 73.40 GiB

KV 预算：
73.40 − 33.74（权重）− 33.20（激活峰值）− 0.13（其他）
≈ 6.33 GiB

但规划检查认为 PP0 支持 150000 token 至少需要 10.04 GiB，因此提前失败。证据见 PP0 profiling 日志 (start_2.log:15)和容量检查日志 (start_2.log:384)。

这里需要注意：

激活峰值是计算时临时使用的空间，不是一直占着的权重。 profiling 后这些临时张量可能已释放，但预算仍要扣除这部分，为正式处理请求留空间。所以即使此刻设备看起来还有很多空闲，KV 预算仍可能不足。



=================150000 token 至少需要 10.04 GiB怎么计算的================
10.04 GiB 是规划器按“各缓存组需要的块数之和 × 公共池每块大小”算出来的。新日志能把它精确还原。

先理解两个单位：

- block_size：一个缓存块能存多少 token。
- page_size_bytes：该层一个缓存块占多少字节。

PP0 的规划中有三类缓存组：

| 类型 | 组数 | 每块容纳 token | 150000 token 每组需要的块数 |
|---|---:|---:|---:|
| 前三层普通 attention | 1 | 128 | 向上取整 150000÷128＝1172 |
| index cache | 19 | 2048 | 向上取整 150000÷2048＝74 |
| 后续 attention cache | 19 | 256 | 向上取整 150000÷256＝586 |

于是总块数为：

1172 + 19 × 74 + 19 × 586
= 13712 个块

PP0 公共池每块大小是 786432 bytes，即 768 KiB。这是因为前三层被放在同一个组中，每层每页 256 KiB：

3 × 256 KiB = 768 KiB

最终得到：

13712 × 786432
= 10,783,555,584 bytes
= 10.04296875 GiB
≈ 10.04 GiB

这个结果与容量检查日志 (start_2.log:384)完全一致。


=================为什么TP8 预算能成功=================
TP8 能通过 0.8 的预算检查，主要不是因为它剩余显存更多，而是它规划出的 KV 最低需求更小。
先说明：这份 TP8 日志实际使用的是 0.9，见第 13 行 (start_tp8.log:13)。下面的 0.8 预算是假设其他开销不变进行换算。

单位均为 GiB：

| 指标 | TP8 每卡，基本一致 | PP8 的 PP0 |
|---|---:|---:|
| 模型权重 | 55.00 | 33.74 |
| profiling 激活峰值 | 10.45 | 33.20 |
| 其他计入开销 | 2.20 | 0.13 |
| 非 KV 总预算开销 | 67.65 | 67.07 |
| 0.9 时 KV 预算 | 14.92 | 15.51 |
| 推算 0.8 时 KV 预算 | 5.75 | 6.33 |
| 规划检查要求的最低 KV | 3.27 | 10.04 |
| 0.8 时预算检查 | 能通过 | 不能通过 |

这修正了此前不完整的解释：PP0 激活峰值虽然大，但权重较少，抵消后它的非 KV 总开销甚至比 TP8 每卡略低。 因此，不能把预算失败单独归因于激活峰值。

真正决定检查结果的是：

TP8：剩余约 5.75 GiB > 规划要求 3.27 GiB → 通过

PP0：剩余约 6.33 GiB < 规划要求 10.04 GiB → 失败

TP8 的最低需求见容量检查日志 (start_tp8.log:42)。



====================TP8 150000 token 只需要 3.27 GB===============
TP8 的 3.27 GiB，是每张卡保存一条 150000 token 请求所需的 KV 大小。 日志可以精确还原：

每 128 token 的全部缓存大小 × 所需块数
= 2,998,272 bytes × 1172
= 3,513,974,784 bytes
≈ 3.27 GiB

具体分三步。

1. 算每 128 token 要保存多少数据

TP8 中，每张卡都承载全部 60 层的部分计算。日志显示，这张卡上的缓存分为：

| 缓存类型 | 数量 | 每个缓存存 128 token 占用 |
|---|---:|---:|
| 前 3 层的 BF16 attention KV | 3 | 64 KiB |
| 后 57 层的 FP8 attention KV | 57 | 32 KiB |
| 后 57 层的 FP8 index cache | 57 | 16 KiB |

加起来：

3 × 64 KiB + 57 × 32 KiB + 57 × 16 KiB
= 2928 KiB
= 2,998,272 bytes

例如，后 57 层中，每层的 attention KV 大小是：

128 token × 1 个本地 KV head × 128 维 × K/V 两份 × 1 byte
= 32768 bytes
= 32 KiB

前 3 层用 BF16，每个元素 2 bytes，因此是 64 KiB。index cache 只有一份索引向量，是 16 KiB。

2. 算 150000 token 需要多少块

所有这些缓存在 TP8 日志中统一按 128 token 一块：

向上取整（150000 ÷ 128）= 1172 块

最后一块即使没装满，也要分配完整空间。

3. 相乘得到最低需求

1172 × 2,998,272
= 3,513,974,784 bytes
= 3.27246 GiB
≈ 3.27 GiB

这与日志中的 required_bytes=3513974784 (start_tp8.log:42)完全一致。

这里的 3.27 GiB 是每卡一条最大长度请求的 KV 需求，不包含权重、计算临时空间和其他运行开销，也不是服务最终会分配的全部 KV。



==========================PP0 的 33.20 GiB 激活峰值====================
PP0 的 33.20 GiB 激活峰值，确认出现在多模态编码阶段。

| PP0 阶段 | 当前 allocated | 累计峰值 |
|---|---:|---:|
| 编码器运行前 | 33.96 GiB | 33.96 GiB |
| 编码器运行后 | 35.67 GiB | 67.16 GiB |
| 语言模型模拟计算后 | 35.67 GiB | 67.16 GiB |
| 清理后 | 33.96 GiB | 67.16 GiB |

所以：

67.16 − 33.96 ≈ 33.20 GiB

见编码器前后日志 (/D:/vllm/vllm/pool_pp.log:74)。后续语言模型计算没有再抬高峰值。

结合此前 TP8 数据，现在可以确认：

- PP8 的 PP0：编码器阶段峰值增量约 33.20 GiB。
- TP8：编码器阶段每卡峰值增量约 10.45 GiB。
